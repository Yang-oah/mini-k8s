# G4 双节点调度与验收设计

G4 的完成条件是 [Gateway.md](../Gateway.md) 中 G4-01 至 G4-06 全部通过，并保留控制面和两个真实 Worker 的证据。`scripts/acceptance/g4.sh` 当前只检查双节点 SSH 连通性及基本环境，始终返回 `BLOCKED`；它不能代替正式验收，也不会创建 Pod、操作 CRI 或配置网络。

## 验收环境

- 两台不同的 Linux Worker，各运行本项目 Agent，并分别连接本机 containerd CRI 和已经配置好的 CNI。可以在一台物理服务器上使用两台独立 Linux 虚拟机：每台须有独立内核、containerd、CNI、PodCIDR 和互通路由。仅在同一个内核/CRI 下启动两个 Agent 进程不能证明跨节点行为。
- 控制面运行 etcd、API、controller 和 scheduler；Agent 与控制面使用节点独立身份。正式场景由 scheduler 绑定，不能手工调用绑定接口。
- 两个 Worker 的 Pod 网段不重叠，节点间已配置到对端 Pod 网段的路由；测试前核实路由与防火墙，不由验收脚本更改。
- 两侧预拉取同一 digest 的测试镜像。G4-05 的镜像还需支持监听 TCP 并以唯一实例标识响应，同时支持作为客户端发起独立 TCP 连接；不要假设任意 busybox 镜像均提供所需功能。
- 测试资源使用独立名称、标签和 UID。测试前记录两节点的 Node UID、allocatable、reserved、Pod/容器/网络租约基线；不得直接清理不属于本次验收的资源。
- 记录源码版本和运行组件的实际版本。G3 的通过记录须能关联到已验收的代码版本；如果 G4 改动影响前序能力，应按要求重新验证，而不能拿另一版本的结果代替。

以下命令只做无密码 SSH 与主机身份预检。目标须已存在于 SSH `known_hosts`，并能使用 SSH 密钥或现有代理非交互登录；需要非默认端口时使用 SSH 配置别名。

```sh
G4_WORKER_A=worker-a G4_WORKER_B=worker-b bash scripts/acceptance/g4.sh
```

预检证据写在输出的 `artifacts/acceptance/...` 目录中。预检会检查两台主机的 Linux 标识、启动 ID 和 `crictl` 命令是否存在，但不会证明它们具备操作权限、容器运行时可用或跨节点网络可用。

## 测试集群启动配置

以下步骤以测试专用控制面和两台已准备好的 Worker 为例。先参考 [G1 说明](g1.md)创建专用目录、CA、服务端证书及 etcd；要将服务端证书扩展中的 SAN 换成 **两个 Worker 实际访问 API 所使用的 IP 或 DNS 名称**。同时生成 `node-a.token` 和 `node-b.token` 两个不同令牌，在 API 身份文件的 `agents` 中分别配置 `node-a`、`node-b`；其他身份仍是 `admin`、`scheduler`、`controller`，所有令牌互不相同。不要向 Worker 分发 CA 私钥、服务端私钥、管理员令牌或对方的节点令牌。

对于**新建的测试专用目录**，可在生成 CA 和服务端证书后、启动 API 前运行下面的命令生成双节点身份。此命令会覆盖该目录中同名身份文件，不能用于正在运行的集群：

```sh
python3 - <<'PY'
import json, os, pathlib, secrets
directory = pathlib.Path(os.environ['MINI_K8S_DIR'])
names = ('admin', 'scheduler', 'controller', 'node-a', 'node-b')
tokens = {name: secrets.token_hex(32) for name in names}
for name, value in tokens.items():
    (directory / (name + '.token')).write_text(value + '\n', encoding='utf-8')
auth = {name: tokens[name] for name in ('admin', 'scheduler', 'controller')}
auth['agents'] = {name: tokens[name] for name in ('node-a', 'node-b')}
(directory / 'auth.json').write_text(json.dumps(auth), encoding='utf-8')
PY
```

在控制面仓库根目录设置以下变量：`MINI_K8S_DIR` 为保存证书、身份文件和 etcd 数据的私有目录，`G4_API` 为含证书匹配地址的 HTTPS origin，`G4_LISTEN` 为两个 Worker 可以访问的控制面本机监听地址及端口。以下构建适用于控制面的 Go 和目标架构；不要将未加密的 etcd 暴露到网络。

```sh
umask 077
mkdir -p "$MINI_K8S_DIR/bin"
go build -o "$MINI_K8S_DIR/bin/mini-api" ./cmd/mini-api
go build -o "$MINI_K8S_DIR/bin/mini-k8s" ./cmd/mini-k8s
go build -o "$MINI_K8S_DIR/bin/mini-manager" ./cmd/mini-manager
go build -o "$MINI_K8S_DIR/bin/mini-scheduler" ./cmd/mini-scheduler
go build -o "$MINI_K8S_DIR/bin/g4-probe" ./cmd/g4-probe

# etcd 已按照 G1 说明启动在控制面本机 127.0.0.1:2379。
"$MINI_K8S_DIR/bin/mini-api" -listen "$G4_LISTEN" \
  -etcd http://127.0.0.1:2379 -tls-cert "$MINI_K8S_DIR/server.pem" \
  -tls-key "$MINI_K8S_DIR/server.key" -auth-file "$MINI_K8S_DIR/auth.json" \
  > "$MINI_K8S_DIR/api.log" 2>&1 &
API_PID=$!
"$MINI_K8S_DIR/bin/mini-manager" -server "$G4_API" -ca-file "$MINI_K8S_DIR/ca.pem" \
  -token-file "$MINI_K8S_DIR/controller.token" -resync 2s > "$MINI_K8S_DIR/manager.log" 2>&1 &
MANAGER_PID=$!
"$MINI_K8S_DIR/bin/mini-scheduler" -server "$G4_API" -ca-file "$MINI_K8S_DIR/ca.pem" \
  -token-file "$MINI_K8S_DIR/scheduler.token" -resync 2s > "$MINI_K8S_DIR/scheduler.log" 2>&1 &
SCHEDULER_PID=$!
```

在两个 Worker 上分别编译同一版本的 `go build -o /实际路径/mini-agent ./cmd/mini-agent`，或从可信构建机分发与 Worker 架构相符的二进制。将 CA 公钥证书和对应节点令牌以受保护方式分别放到各 Worker 的本地文件中。节点必须先由管理员注册；下面的 `allocatable` 示例值仅在确实可用时采用，PodCIDR 必须替换为每台机器实际 CNI 网段，且互不重叠：

```sh
export G4_CLI="$MINI_K8S_DIR/bin/mini-k8s" G4_CA="$MINI_K8S_DIR/ca.pem"
export G4_ADMIN_TOKEN="$MINI_K8S_DIR/admin.token"
mini() { "$G4_CLI" --server "$G4_API" --ca-file "$G4_CA" --token-file "$G4_ADMIN_TOKEN" "$@"; }
cat > "$MINI_K8S_DIR/nodes.yaml" <<EOF
apiVersion: mini.k8s/v1
kind: Node
metadata: {name: node-a}
spec:
  allocatable: {cpuMilli: 2000, memoryBytes: 1073741824}
  podCIDR: $G4_POD_CIDR_A
---
apiVersion: mini.k8s/v1
kind: Node
metadata: {name: node-b}
spec:
  allocatable: {cpuMilli: 2000, memoryBytes: 1073741824}
  podCIDR: $G4_POD_CIDR_B
EOF
mini apply -f "$MINI_K8S_DIR/nodes.yaml"
mini get nodes
```

在每个 Worker 的测试 shell 中分别设置 `G4_API`、`G4_NODE`（`node-a` 或 `node-b`）、`G4_AGENT`、`G4_CA_FILE`、`G4_NODE_TOKEN_FILE`，并确认本机 CRI endpoint。下面命令使用本机 CRI 所需权限启动前台进程；日志可由运行者按本机规则保存。各节点的状态目录和日志目录均留在各自机器：

```sh
sudo "$G4_AGENT" -server "$G4_API" -node "$G4_NODE" \
  -ca-file "$G4_CA_FILE" -token-file "$G4_NODE_TOKEN_FILE" \
  -cri-endpoint unix:///run/containerd/containerd.sock \
  -state-dir /var/lib/mini-k8s/agent -log-dir /var/log/mini-k8s -resync 2s
```

启动后检查三个控制面进程和两台 Agent 日志，利用 `mini get nodes` 确认两个节点健康及心跳。成功启动不代表 G4 已通过。停止进程或做断连实验前先记录确切进程身份，避免误操作已有服务；故障注入必须保留数据面并且能够恢复。

## 人工取证命令

先根据 [G1 操作说明](g1.md#操作示例)准备 API URL、CA、管理员 token 文件及 CLI 二进制。以下变量均为示例路径，替换为实际测试环境；token 内容不要写入日志或命令行。临时证据目录可能包含资源元数据，应限制权限。

```sh
export G4_API='https://控制面地址:8443'
export G4_CA='/实际路径/ca.pem'
export G4_ADMIN_TOKEN='/实际路径/admin.token'
export G4_CLI='/实际路径/mini-k8s'
umask 077
G4_EVIDENCE="$(mktemp -d)"
mini() { "$G4_CLI" --server "$G4_API" --ca-file "$G4_CA" --token-file "$G4_ADMIN_TOKEN" "$@"; }
date -u +%FT%TZ > "$G4_EVIDENCE/start.txt"
mini get nodes > "$G4_EVIDENCE/nodes-before.json"
mini get pods > "$G4_EVIDENCE/pods-before.json"
mini get rs > "$G4_EVIDENCE/replicasets-before.json"
```

分别登录两个 Worker，以具有 CRI 权限的用户只读记录基线。`crictl` 的 endpoint 应与该 Worker 的 Agent 一致；先确认网络名和租约目录，再自行将路径替换到 `ls` 命令中。

```sh
date -u +%FT%TZ
ip -4 route show
sudo crictl --runtime-endpoint unix:///run/containerd/containerd.sock info
sudo crictl --runtime-endpoint unix:///run/containerd/containerd.sock pods -o json
sudo crictl --runtime-endpoint unix:///run/containerd/containerd.sock ps -a -o json
sudo ls -la /var/lib/cni/networks/实际网络名
```

创建测试 RS 时，将专用清单中的镜像、requests、limits 和唯一标签按场景修改，再用 `mini apply -f 测试RS.yaml` 提交；提交前后使用 `date -u +%FT%TZ` 记录时间。使用 `mini get pods`、`mini get nodes` 和 `mini get rs 测试RS名` 保存每次快照，结合两侧 `crictl pods -o json`、`crictl ps -a -o json` 按 Pod UID 核对真实实例。伸缩命令为 `mini scale rs 测试RS名 --replicas 4`（依次改为 1、0）；每次变更后立即记录时间并持续检查，直到达到该步要求。最终再次采集上述三类 API 快照以及两侧的 CRI 和租约基线，按 UID 比对。

这些命令是操作入口和取证材料，不会自动证明时限或并发期间的每一次状态变化。`g4-probe` 提供下文的并发请求、周期采样和 TCP 检查，但采样不能覆盖两次采样之间的状态；还需要完整绑定事件证据、真实运行时对照及仅断开控制连接而保留数据面的可恢复故障注入。缺失的证据应标记 `BLOCKED`，不能只凭最终快照判通过。

## 并发和时间序列辅助工具

`g4-probe create` 根据一个 JSON 格式的独立 Pod 模板并发创建 Pod，不绑定、不删除、不重试。模板中的名字会由 `-name-prefix` 覆盖；每次运行选择未使用的新前缀。模板不能包含 UID、ownerUID、NodeUID、已填充的状态或其他系统管理字段。将 `IMAGE_DIGEST` 换成两台节点已具备的真实 digest，按 CPU 或内存场景修改 requests；以下示例不是通用的超额参数，须依据两节点剩余容量计算：

```sh
cat > "$MINI_K8S_DIR/g4-pod.json" <<'EOF'
{
  "apiVersion":"mini.k8s/v1", "kind":"Pod",
  "metadata":{"name":"template", "labels":{"app":"g4-overcommit"}},
  "spec":{"image":"IMAGE_DIGEST", "restartPolicy":"Always",
    "command":["/bin/sh", "-c", "while true; do sleep 60; done"],
    "resources":{"requests":{"cpuMilli":500,"memoryBytes":67108864},
                 "limits":{"cpuMilli":500,"memoryBytes":134217728}}}
}
EOF
```

确保模板内容已替换且节点预拉取匹配镜像后，先启动观测，再在另一个 shell 运行并发创建。输出文件含测试资源身份，应置于私有证据目录；`G4_EVIDENCE` 按前节创建。

```sh
"$MINI_K8S_DIR/bin/g4-probe" observe -server "$G4_API" -ca-file "$G4_CA" \
  -token-file "$G4_ADMIN_TOKEN" -duration 60s -interval 1s \
  > "$G4_EVIDENCE/api-series.jsonl" &
OBSERVER_PID=$!

"$MINI_K8S_DIR/bin/g4-probe" create -server "$G4_API" -ca-file "$G4_CA" \
  -token-file "$G4_ADMIN_TOKEN" -manifest "$MINI_K8S_DIR/g4-pod.json" \
  -name-prefix g4-cpu-20261104a -count 6 \
  > "$G4_EVIDENCE/cpu-creates.jsonl"
CREATE_STATUS=$?
wait "$OBSERVER_PID"
OBSERVE_STATUS=$?
printf 'create=%s\nobserve=%s\n' "$CREATE_STATUS" "$OBSERVE_STATUS" > "$G4_EVIDENCE/exit-status.txt"
```

前缀只允许小写英文字母、数字、连字符，需将示例替换为本次唯一值。单次创建最多 200 个 Pod；两个场景应使用不同文件和前缀，先完成上一场景的 UID 清理。返回超时不代表请求未落库，应先按结果中的名称查询 API 和运行时，切勿立即用另一名称重试。程序有任何请求错误时返回非零，结果逐条包含名称、请求起止时间、HTTP 状态及确认取得的 UID；不会输出 Pod 环境变量或 token。

`observe` 记录每次采样的开始/结束时间、节点容量与预留、Pod 请求量/UID/状态；节点和 Pod 分别读取，因此一次记录不是跨资源原子快照，且两次采样间的短暂变化可能被遗漏。观测结果可辅助判断，并不能单独证明全部并发绑定从未超额或在规定时限内完成。结合 API 事务/事件与真实 CRI 证据进行审查，尚无可靠事件链时标记 `BLOCKED`。

## 双向 TCP 辅助工具

`g4-probe serve` 监听 TCP，每次返回实例标识；默认标识为容器 hostname。项目运行时将 Pod 名称设为 sandbox hostname，测试前仍需以 `crictl inspectp` 核对目标 Pod UID、容器及 hostname 的实际对应关系。`check` 每次重新拨号、读取一次响应并关闭连接；失败也会记录，任何一次失败均返回非零。

在与 Worker 架构一致的 Linux 构建环境生成静态二进制，然后由用户用可信镜像构建工具制作测试镜像，并将固定 digest 预置到两台 Worker。示例仅展示输入文件，不会自动构建、推送或导入镜像：

```sh
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o g4-probe ./cmd/g4-probe
cat > Dockerfile.g4-probe <<'EOF'
FROM scratch
COPY g4-probe /g4-probe
ENTRYPOINT ["/g4-probe"]
EOF
```

实际架构不是 amd64 时需改用对应 `GOARCH`；将测试工作负载命令设为 `[/g4-probe, serve, -listen, :8080]`。两个测试 Pod 在不同节点运行后，在各自节点查明对应的 container ID、Pod IP 和 hostname，使用 crictl 在两个容器中分别运行（将占位符替换为实际值）：

```sh
# Worker A 的测试容器中访问 B；在 Worker B 对 A 重复，交换 IP 和目标名称。
sudo crictl --runtime-endpoint unix:///run/containerd/containerd.sock exec \
  A的容器ID /g4-probe check -target B的PodIP:8080 -expect B的Pod名称 -count 10
```

分别保存两方向的 10 条 JSON 记录及命令退出状态。每条包含连接起止时间、源/目的地址和响应身份；核对来源确实位于相应 Pod 网络命名空间，目标身份与 CRI 证据一致。若镜像无法运行 `crictl exec`、hostname 不匹配、任一连接失败或缺少一方向记录，该检查不能标记 PASS。

## 各项场景与证据

1. **自动调度（G4-01）**：在已知空闲容量上设置测试 requests，使任一节点均最多容纳该工作负载的一个副本；提交 2 副本 RS，记录提交时间、请求量、容量基线及每个 Pod 的 UID、绑定节点、Running 时间与对应 CRI 实例。须在 30 秒内各运行一个，不得用均衡评分代替容量约束。
2. **并发超额（G4-02）**：分别构造 CPU 和内存超额场景；内存场景的 CPU 请求不能先成为瓶颈。并发创建测试 Pod，持续记录绑定及节点预留，检查同一 UID 不重复绑定、预留始终不超过 allocatable，未调度的 Pod 10 秒内为 Pending 且给出资源不足原因。
3. **释放再调度（G4-03）**：记录运行中 Pod UID，删除它并确认其本机 CRI sandbox、容器和 CNI 租约清理完成，再检查预留仅释放一次，以及等待的 Pod 在 30 秒内自动运行。重复清理时预留不能为负。
4. **节点失联（G4-04）**：仅断开一个 Agent 的控制连接，保留其容器和数据面网络；记录最后有效心跳时间。20 秒内应显示 Unknown，此后新 Pod 不能绑定该节点；连续观察 30 秒确认旧 RS Pod 没有被自动替代。恢复连接后确认原实例与两节点健康，再进入下一场景。
5. **跨节点 TCP（G4-05）**：在健康的两个节点各运行一个可识别的测试实例，从两个 Pod 分别向对方新建 TCP 连接各 10 次。记录每次响应，全部成功且响应标识为目标实例；ping 或重复使用一条连接均不满足要求。
6. **伸缩清理（G4-06）**：使用两节点均可容纳的小 requests，依次执行 RS 2→4→1→0；记录每次变更时间、Pod UID 及真实运行数，每步 30 秒内收敛。结束时核对两个节点的 CRI、CNI 租约与预留均回到本轮测试前基线。

断言失败、超时、中断或资源清理无法确认时保留本次 UID、运行时身份与现场，不自动删除其他工作负载，也不擅自重装节点。记录测试时钟、操作起点和检查时间，避免仅根据最终快照推断时间要求。必须同时取得 API 和相关 Worker 的真实运行时证据；缺失证据时为 `BLOCKED`，实际断言失败时为 `FAIL`。

## 尚待接入的执行器

目前没有自动化双节点 G4 执行器。后续接入时，执行器须具备可验证的测试集群身份、按 UID 限定的资源操作、对双方 CRI 和 host-local 租约的只读观测，以及可恢复的 Agent 控制连接故障注入。其报告只有在六项断言和清理核对全部完成后才能输出 `PASS`，不能根据本预检生成通过结果。
