# G5 收尾与可靠性增强规划

本文整理 G5 收尾及后续可靠性工作的实施顺序，是设计与排期依据，不修改 `Plan.md` 和 `Gateway.md` 中已有的验收结论。实现和验收脚本由开发侧准备，Linux 环境验证由用户执行；每个模块分别提交 PR，验收通过后再合并，不直接推送主分支。

## 0. G5 验收收尾

**目标：** 按 Gateway 认可已经测得的行为，补齐真正缺失的证据，而不是因为采集器固定输出 `BLOCKED` 或缺少额外的规则全文而重做整轮测试。

- **保留测量：** G5c 已记录 Service 四路访问、端点摘除与重连、无端点拒绝、组件重启以及 20 Pod 发布与伸缩；每项仍需按对应 Gateway 条款核对原始文件和身份、时间、版本。G5-05 的已有判定文件记录为 PASS，其他项不因本规划自动判定通过。
- **修复采集口径：** API 采集器区分采集结果和 Gate 结论；两侧节点使用全规则采集时，先等待各自 `READY` 并检查样本，再进行删除。`READY` 不是验收通过。
- **优先核对和补采：** 先核查 G5-01 两侧容器访问记录的来源、时间和身份；G5-07 的 node-a 租约与两侧规则如果原证据不能覆盖删除后的 30 秒，只补测清理场景。终态采样须从删除成功后开始、在时限内结束，并考虑节点时钟误差。
- **前置准备：** 两台节点需能通过交互 sudo 运行采集器，准备来源经管理员核验的 root 所有 `crictl` 与受保护的证据目录。采集之前先验证权限，避免测试后才发现无法读取。
- **已登记的限制：** Service 删除后永久保留 ClusterIP 声明，避免失联 Proxy 的旧规则指向新工作负载。[Gateway G5-07](../Gateway.md#7-g5service-与整体-demo) 的回归基线指本轮 Pod 的 CNI 租约、节点预留和已删除 Service 的转发规则，不要求地址池可用数回到测试前。`retained` 不能写成已释放。
- **退出条件：** 对照 [Gateway G5](../Gateway.md#7-g5service-与整体-demo) 汇总 G5-01～07；关联同一最终版本的 G1～G4、安装/示例/排障验证及已知限制。取证细节和补采步骤见 [G5c 证据核对](g5-evidence-reconciliation.md)。

## 模块交付约定

1. **设计：** 写清适用版本、范围、依赖、不变量、故障语义和不做的事项；对数字先标注测量方法和假设，不把目标当作实测结果。
2. **实现：** 使用独立分支，维持现有代码规范与必要注释；修改公共接口或存储契约时记录兼容与恢复方式。
3. **验证：** 开发侧提供测试与操作步骤，用户在约定环境执行；按变更影响选择已有场景回归，保存源码版本、运行配置、操作时间和证据。
4. **交付：** 检查项通过、证据与限制可核对后提交并合并对应 PR；失败保留结果并修复，不覆盖原有记录。

## 目标与范围

在单控制平面、单成员 etcd、两个 Worker 的现有部署边界内，优先保证请求重试安全、并发下状态正确、负载有界，以及故障后可恢复。先建立可测量的容量基线，再逐步优化读取和对账，不预设本项目已能支撑特定生产规模。

可靠性指标必须区分**安全性**（例如不能重复补建、不能超额预留）和**可用性**（例如多快收敛）。存储结果未知时优先保持安全并继续确认，不以盲目重试换取表面吞吐量。单成员 etcd 和单控制面仍是单点；本阶段不声称高可用或跨网络 exactly-once。

## 现状与主要风险

- API 写入已有 resourceVersion/CAS；调度绑定与资源预留在同一事务中比较并更新。继续保留这些服务端约束，不能依靠客户端缓存替代。
- ReplicaSet 控制器目前单工作者，Watch 只用于触发，按周期和事件重新 List；每个 RS 的对账还会读取 Pod 集合。创建时使用确定名称及失败后查询，但尚非 PRD 所述的持久化操作流水。多 RS 或事件增多时可能产生额外读取，具体瓶颈须通过压测确认。
- Agent 的运行时操作和清理已有并发控制与重试状态；具体参数和覆盖范围须以实现及测试核对，不能将局部并发上限视为全系统限流。
- 服务端已有 etcd Watch 转发；当前设计尚需明确慢消费者、连接数量、资源占用和缓存重建的整体边界。仅凭 Watch 连通不能证明长期一致性。
- G5 的 readiness 代次处理不等同于完整节点会话栅栏。节点失联时默认不补副本；只有完成外部隔离与相应栅栏设计后才可考虑人工驱逐。

## 一致性与失败语义

1. etcd 是唯一持久化状态源，只有 API Server 直接访问；缓存仅用于观察和加速，不能取代事务内版本、UID、所有权和节点容量校验。
2. 每个修改必须明确成功、确定失败或结果未知。请求超时不证明事务失败；未知结果使用原操作身份查询并重试，不换身份制造第二次副作用。
3. 对已存在的操作 ID，同一请求摘要返回既有结果；同 ID 不同摘要返回冲突。记录与目标写入必须同事务提交；无法确认时保留未知状态。记录回收需同时满足对象生命周期和客户端重试窗口，并防止过期重试变成新操作。
4. 409 后重新读取并重新计算；临时错误使用有上限、带抖动的退避。错误重试必须受队列容量和总超时预算约束，避免故障期间放大流量。
5. 同一对象由 UID 识别，同名重建视为新对象；终态不能复活。对已绑定 Pod，清理确认或符合后续隔离协议之前，副本额度和预留不能提前释放。

## 建议分模块实施

### R1：容量基线与写入幂等

**依赖：** G5 收尾；继续保持单个活跃 Controller Manager。**交付：** 基线记录、操作身份与结果查询、超时恢复逻辑、对应验证说明。

操作记录、事务边界与分批交付见 [R1 详细设计](r1-reliability-design.md)。

已完成的只读采样验证与尚缺的完整容量数据见 [R1-A 验证记录](r1-baseline-results.md)；采集步骤见 [R1-A 采集说明](r1-baseline.md)。

先盘点创建、删除、绑定、状态更新和清理的现有重试路径、操作身份和可能的未知结果；建立统一故障注入与指标采集方式。优先为 RS 补建设计持久化操作 ID、请求摘要及查询结果，并在同一 etcd 事务提交操作记录和创建结果。控制器重启后恢复未决操作并强一致重读；确定性名称继续作为辅助保护，而不是替代操作记录。

当前保持单个 Controller Manager 活跃，单 RS 串行。若未来允许多个控制器实例，必须先加入持久化领导租约及写事务代次栅栏；仅用进程内锁不足以跨进程互斥。操作记录容量与清理机制要在实现前给出可配置边界和过期重试处理，不允许无界增长。

**验收：** 记录 1、8、32 客户端及 20、40 对象的基线；并发请求、提交成功后响应丢失、控制器重启和同名 RS 重建场景均不重复补建。未知结果能用同一操作 ID 核对，同 ID 不同内容返回冲突；过期处理及容量上限有明确行为。这些负载数是初始实验点，非性能承诺。

### R2：etcd 访问、有界并发与缓存

**依赖：** R1 的幂等和负载基线。**交付：** etcd 访问预算、并发与队列限制、控制器本地索引缓存、超载反馈及观测；API Server 共享缓存另行根据实测评估。

以实测结果决定优化点。控制器可引入按 RS UID 去重的有界队列：同一 UID 串行、不同 UID 最多 N 个工作者；队列满时合并信号并安排重新 List/全量校正，不静默丢掉最终状态。Worker 数、队列长度及 API 在途请求数可配置，有合理默认值并提供在途、积压、拒绝和耗时指标；初始数值是压测参数，不是吞吐承诺。

建立控制器本地索引：一致 List 获得 revision，从其后 Watch；按资源 UID 和 revision 处理重复及旧事件。同一事务可能产生同一 revision 的多个对象事件，不能按全局 revision 去重而遗漏对象。断线无法证明连续、历史压缩、队列溢出或缓存不可信时丢弃受影响索引并重新 List，恢复前暂停依赖该索引的写决策。周期性校正仍保留。不同资源集合的快照不应假定天然处于同一 revision；跨资源的关键决策必须由 API 事务或强一致重读保护。

API 的普通请求、Watch 连接及慢消费者分别设置资源预算；普通请求过载应及时返回可识别错误，避免挤占心跳与恢复所需容量。Watch 不能无限缓冲，慢消费者断开后重新 List；不能让慢消费者阻塞其他订阅或写入。不得用缓存中旧的空闲容量决定最终绑定。

**验收：** 在配置上限内与超限分别施压，记录吞吐、延迟、队列和内存；检查同一 RS 串行、不同 RS 并发及超额调度安全。对 Watch 断线、压缩、慢消费者和队列溢出注入故障，验证重新 List 后与强一致状态一致；与 R1 基线比较，不预设优化收益。

#### etcd 与缓存专项设计

这里的“etcd 缓存”指 **mini-k8s 组件中维护的 etcd 数据视图**，不是把缓存部署到 etcd 内，也不是再引入一套独立数据库。etcd 仍是唯一持久化事实来源，只有 API Server 直接连接 etcd。

```text
etcd <── 强一致读取 / CAS 事务 ──> API Server <── List / Watch ──> Controller 本地缓存
                                  │
                                  └── 其余组件通过 API 访问
```

| 位置 | 用途 | 一致性边界 |
| --- | --- | --- |
| Controller 本地缓存 | 保存 RS、Pod 等资源的观察快照与按 owner UID 的索引，减少重复 List | 只加速对账；缓存未同步或连续性无法证明时不得依据它做有副作用的决策，关键创建结果须强一致确认 |
| API Server 共享缓存（候选） | 多组件反复读取成为瓶颈时，评估复用 List/Watch 和只读快照 | 默认不改变现有 API 的读取一致性；若要提供可能过期的读取，须新增明确契约并单独验收，不能静默替换强一致读取 |
| etcd | 保存资源、版本、操作记录和事务结果 | 所有写入及关键状态比较仍在 etcd 事务中完成；缓存不可异步代写或自行宣称提交成功 |

按以下顺序拆分实施，每一步可单独形成 PR：

1. **访问与容量基线：** 记录请求类型与数量、etcd 读写延迟、Watch 数量、错误和超时、数据库及磁盘用量；对 20/40 对象和 1/8/32 并发测量，作为初始测试点而非容量承诺。核查现有连接复用、请求期限和取消传播，先修复可观测到的重复读取和无界请求。
2. **访问保护：** 对普通 API 请求、etcd 在途操作和 Watch 分别设上限，保留心跳和恢复路径的资源预算；过载明确返回可识别错误。临时失败使用有界退避；etcd 不可用时不以缓存伪造写入成功，超时写入按 R1 的操作 ID 查询确认。
3. **控制器缓存：** 通过 API 完成 List/Watch 同步并维护按资源 UID、owner UID 的索引，按 RS UID 去重入队。缓存启动未完成、Watch 中断无法确认连续、压缩、队列溢出或解码失败时暂停依赖该缓存的写决策，重新 List 并建立 Watch；恢复前后的 resourceVersion 和错误均可观测。内存、队列和订阅数量须有配置边界及溢出行为。
4. **按需评估 API 缓存：** 若基线仍显示 etcd 读取或 Watch 扇出是瓶颈，再提出独立设计，说明快照 revision、慢消费者、缓存失效、授权过滤、强一致读取和写后读语义；先做兼容性及故障验证，不能仅以 TTL 判断状态一定新鲜。
5. **存储维护与恢复：** R4 交付快照、压缩/碎片整理的运维评估与操作手册，以及磁盘配额、水位、告警和恢复演练。压缩可能导致旧 Watch 失效，必须与缓存重建配套；维护操作不得自动清理未经确认的业务键或操作记录。单成员 etcd 不能因引入缓存就获得高可用。

**专项验收：** 同版本比较缓存启用前后的 etcd 请求量、P50/P95/P99、内存和最终收敛时间；验证 Watch 首次 List 的交界、断线、压缩、慢消费者、队列溢出和同 revision 多对象事件。注入缓存落后、etcd 中断和提交后响应丢失，验证无重复创建、无超额预留，恢复后缓存与强一致读取一致；无法满足前提时保持未就绪或返回错误。压测阈值和磁盘水位由基线与资源预算确定，不能把缓存命中率单独当作可靠性通过。

### R3：节点会话与隔离恢复

**依赖：** R1 的操作身份和基本一致性约束；与 R2 共用有限并发和恢复机制。**交付：** 会话协议、Agent 对账、人工隔离驱逐及节点恢复说明。

持久化 Node UID、单调会话代次和会话阶段；失联与代次推进同事务完成。心跳、Pod 状态及探测上报在写事务中校验当前节点身份、会话及 Pod UID/版本，不能只在写入前检查。恢复会话先对账容器身份并重新探测 readiness，再允许端点接流量。

人工驱逐以实际外部隔离为前提，并记录操作 ID、操作者及原因；按 PRD 要求原子撤销旧会话、终态化关联 Pod 和释放预留。若事务大小超过存储上限，必须在提交前明确拒绝且不产生部分效果，不能悄悄改为分批释放。凭据重新授权、旧会话禁止领取新权限及错误隔离的风险要单独设计；会话栅栏本身不能停止分区节点的进程。

**验收：** 节点断连与恢复期间旧会话的心跳、状态和探测写入被拒；新会话完成对账和新的探测前不能恢复端点。未做外部隔离时不补建；完成隔离后的驱逐可安全重试、预留不重复释放；超出事务限制时整项拒绝且无部分副作用。

### R4：故障恢复与运维可靠性

**依赖：** 前述模块的版本、操作及会话语义；快照和审计可拆为独立 PR。**交付：** 备份恢复手册、审计恢复流程和最小运行观测。

实现并演练 etcd 快照备份和离线恢复，清楚记录快照时点及可能丢失的变更；节点重新接入时按 UID 对账。按 PRD 单独设计审计意图/结果关联、未决操作恢复及磁盘满门控；不能假定审计日志与 etcd 跨存储原子提交。持续观测请求延迟、错误、队列积压、缓存重建、操作未知数、etcd 空间与恢复耗时，并限制日志敏感信息。

**验收：** 独立演练 etcd 短暂停止恢复与快照离线恢复，记录快照后的丢失窗口；验证审计不可写、操作结果未知及恢复对账，证据不足时保持未知并告警。检查关键指标能定位失败，且输出不含凭据。

## 验收设计

用户负责运行验证；每个模块按独立 PR 提交并在验收后合并。验证记录需绑定源码提交、构建产物、配置和测试环境；不同源码版本的结果不能直接合并为同一版本的结论。G5 既有测试结果继续保留，新增可靠性验证针对本模块增量，不要求无理由重做全部历史测试；涉及旧功能的改动应安排有针对性的回归。

在 PRD 的 1 控制面、2 Worker、20 Pod 环境上先建立无优化基线。建议以 1、8、32 个并发客户端及 20、40 个对象作为初始测试点，并另测超出配置上限的请求；这些是实验输入，不是已验证容量或最终 SLA。记录成功/拒绝/超时数、P50/P95/P99 延迟、收敛时间、最大队列与在途量、内存、etcd 请求量和存储增长。固定预拉取镜像、资源配置、负载持续时间及采样方法后比较前后结果。

每项至少验证以下不变量：

| 场景 | 必须观察到的结果 |
| --- | --- |
| 并发创建及响应丢失 | 同操作 ID 重试不重复创建；不同内容复用 ID 冲突；未确认结果不会触发换 ID 补建。 |
| 并发调度与删除 | 同一 Pod 只绑定一次，预留不超容量、不重复释放；对象 UID 替换后旧操作不影响新对象。 |
| 缓存断线、压缩及溢出 | 触发重建，恢复后最终状态与强一致读取一致；重建期间不使用不可信缓存执行危险写入。 |
| 过载与慢消费者 | 请求和内存受配置上限约束，有明确拒绝或断开；正常请求和恢复路径仍可前进。 |
| etcd 短暂停止及恢复 | 新写入失败或结果未知时不冒充成功；已运行容器继续运行；恢复后重新对账，不产生重复副作用。 |
| 节点断连、旧会话与隔离 | 旧会话写入被拒；未重新确认并探测的端点不接流量；未完成外部隔离不自动补副本。 |

实际并发目标、收敛时间和资源预算由基线测量后确定并记录；不达标时先定位瓶颈，再决定是否调整设计或范围。
